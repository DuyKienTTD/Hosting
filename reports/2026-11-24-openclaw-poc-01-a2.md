## 2. Source-derived findings; session routing is not storage isolation

**F-OC01 durable pre-filter raw ingress (P0 test priority):** `ingress.ts` serializes the **full raw zca-js message envelope** using `JSON.stringify(message)`, then creates `ZalouserIngressPayload { version:1, receivedAt, rawMessage }` and calls `monitor.admit(message,{facts})` in `receive`. In `monitor.ts` this monitor's dispatch callback later runs content checks, group allow/mention and per-sender access checks. `ingress.test.ts` includes a test named `finishes the durable append before dispatching` and recovery of a pending event. Hence **SOURCE_REVIEW indicates durable raw admission precedes business-level deny**. The original queue's `retention.completedMaxEntries = 1000` and `failedMaxEntries = 1000` are **entry count caps**, not time-based consent TTL, content redaction or deletion of a denied event. This is a suspected **privacy-policy conflict**, not proof of leakage, and not a runtime test PASS. `monitor.group-gating.test.ts` includes skipped group message history insertion, separate from ingress durability.

**F-OC02 session routing only (P0):** `session-scope.ts` maps absent or `main` DM scope to `per-channel-peer`; `monitor.ts` requests `resolveAgentRoute({channel:'zalouser',accountId,dmScope,peer})` then uses `route.sessionKey` for inbound message routing and group history map key. Distinct keys alone do **not** prove separate on-disk transcripts, agent memory, workspace, vector search, summary, file/media storage, tool results, cache, logs, or model prompt. The same logical `agentId` may still address a shared workspace/memory index. Need inspect and *execute* actual data source resolution, per-scope retrieval with two groups and DM, restart, and inspect negative outputs.

**F-OC03 group-name matching and authorization (P1):** `group-policy.ts` builds candidate keys from group ID, optional `group:<id>`, group channel/name/normalized name (unless allowNameMatching disabled), then wildcard. `resolveZalouserGroupScope` selects first exact candidate; its comment says an exact entry hides wildcard fields. `monitor.ts` calls `isDangerousNameMatchingEnabled`, resolves name candidates/allowFrom, group policy and sender access. A group sharing another group's display name is a negative fixture; group ID must prevail and dangerous name matching must be proven off. Existing `group-policy.test.ts` checks name matching on/off; that does not test data retrieval or persistence isolation.

**F-OC04 in-memory skipped group history (P0):** `monitor.ts` maintains `const groupHistories = new Map<string, HistoryEntry[]>()`. A group unmentioned/filtered after policy checks may be recorded in this map through `channelHistory.record` and later injected via `buildPendingContext` and `buildInboundHistory`, keyed by `route.sessionKey`. `monitor.group-gating.test.ts` has `includes skipped group messages as InboundHistory on the next processed message`. This is an explicit **retention path with no demonstrated independent consent gate**. Verify X/Y separation, opted-out sender exclusion, case of group access revoked between skip and next mention, and restart cleanup. Distinguish ephemeral RAM from durable queue.

**F-OC05 attachment side effects before final use (P1):** `monitor.ts` invokes `core.channel.media.saveRemoteMedia` for attachments after an access decision, then rechecks access/claim and calls `deleteMediaBuffer` on rejected result. This is a local media storage side effect potentially preceding final access/consent; verify filesystem state after DENY, mid-download revoke, abort and restart. The code includes checks but test execution not performed.

**F-OC06 pairing and account scoping (P1):** `monitor.account-scope.test.ts` explicitly tests per-account pairing-store read and request for a `beta` account. This is test code, not runtime proof of global transcript/memory separation. A test with **one synthetic account** is authorized here; cross-account adversarial isolation requires separate approval for a second account if demanded later.

**F-OC07 consent and retention are NOT feature-proven (P0):** DM policy, group policy, allowlists, mention conditions and session scope control processing. In the inspected zalouser files there is **no demonstrated authoritative per-sender/thread consent record with independent `respond`, `retain`, `passiveGroup`, revocation/expiry and atomic write suppression**. Mark `FEATURE_GAP_NOT_PROVEN` rather than assert it exists or that OpenClaw is compliant. A synthetic fake consent policy in the harness may be used as an *oracle* but cannot be counted as native implementation.

**F-OC08 audit command is not acceptance (P2):** `src/security/audit.ts` exists but is a broad security-audit implementation; no actual audit or targeted session-store isolation test was executed by A2. Even a generic PASS security audit would not prove customer privacy without database/file-level evidence.
