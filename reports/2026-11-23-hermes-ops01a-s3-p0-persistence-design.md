## 1. Threat model, contract and invariants

- **Boundary:** producer identity authenticated at admission (e.g. mutually authenticated transport or signed bounded envelope) and mapped *server-side* to tenant/resource/rule/version; a JSON `source` or `rule` string alone, including the D3 optional absent rule, **is not identity proof**. Validate types/size/UTC/finite JSON before allocating identities; reject foreign inputs before replay reservation. Quotas per authenticated principal and resource bound flood. A compromised authorized producer can still generate 256 distinct plausible interruptions; detection and quarantine are required, not an assumption of trust.
- **Identity:** `(tenant, resource, rule, rule_version, producer_epoch, sample_id)` has a UNIQUE constraint **across normal and interruption outcomes**. `producer_epoch` is a server-authorized fence, never chosen by the untrusted sample. Store canonical payload hash and algorithm/version; bytes are D3 sorted compact finite JSON, so timestamp formatting variations of the same instant are a **conflict**, not exact replay. A new canonicalization version needs explicit compatibility mapping; don't silently reinterpret old hashes. Include accepted timestamp and class; exactly one terminal result per identity. No raw sample or secret in public evidence. Hash is an equality check, **not** authenticity. Collision resistance and availability of original canonical bytes in a protected store must be reviewed; never infer replay identity from the diagnostic audit alone.
- **Control state:** one authoritative row per `(tenant,resource,rule,rule_version)` with state, streaks, `last_ts`, alert time, incident sequence, transition revision, committed ledger high-water and active producer epoch. Trusted UNKNOWN/stale/blocked advances neither `last_ts` nor incident identity but atomically records its replay ID and clears both streaks. Fully validated exact/conflicting replay is classified before timestamp comparison, even if watermark catches up. Invalid/foreign input never reserves an ID. A normal good/bad accepted sample and its control update are committed together; accepted sample IDs cannot double-apply. Do not publish a state transition before both identity and state commit.
- **Notification boundary:** do **not** send an external notification inside a database transaction. Write a unique outbox event keyed by `(scope, incident_seq, notification_kind, eligibility_revision)` in the *same* transaction, deliver after commit, and persist attempts/acks separately. Even a unique outbox cannot guarantee exactly-once effects in an arbitrary external channel after timeout/crash; require receiver-side idempotency when available, otherwise document at-least-once/uncertain outcome, reconcile manually before retry, never claim no duplicate delivery. Preserve OPEN/RECOVERED incident identity and +899/+900/+901 cooldown semantics.
- **Snapshot integrity and freshness:** v2 JSON `restore()` checks shape only; Hermes N3 proved that deleting `interruption_replays` and audit can cause a second reset. Replace as a recovery input with a DB-consistent backup/manifest covering identity ledger, control, outbox, schema, revision, epoch, high-water and backup generation; authenticate manifest (HMAC with protected key or signature) and verify data digest. **MAC alone cannot prevent replay of an older valid backup.** Compare monotonic generation/high-water to a *separately protected durable witness* outside the rollback domain (or a quorum/append-only external witness). If witness missing, stale, compromised or recovered DB is older, quarantine ingestion and notifications; reconcile trusted WAL/ledger or require explicit A0-approved rebootstrap with risk disclosure. No automatic reset/epoch change just because old IDs were lost. Keys require least privilege, rotation/overlap and backup separately from data; never put values in repository.

## 2. Two candidate architectures (neither selected for live use)

| Dimension | A — single-host transactional SQLite WAL | B — PostgreSQL transactional ledger + fenced worker |
|---|---|---|
| Storage/concurrency | Dedicated local volume, SQLite WAL, `BEGIN IMMEDIATE` serializes writers per DB; UNIQUE identity ledger, control row, outbox in one transaction. Multi-*process* on same host/local filesystem only; bounded busy timeout, fail closed on `SQLITE_BUSY`. Do not put WAL on NFS/shared network storage. | Dedicated schema/database, UNIQUE identity ledger, `SELECT ... FOR UPDATE` scope row or serializable transaction with bounded retry **only before external effects**. Multiple writers/hosts can use the DB; fence worker ownership by DB-issued generation and reject stale writers. |
| Atomic ingest | Validate/admit; acquire write tx; re-read same-ID ledger before clock; enforce capacity/high-water; insert identity and update state/outbox atomically; COMMIT then acknowledge. For interruption keep `last_ts` fixed. | Same transaction and invariants with row lock + unique constraint. Handle uniqueness/serialization errors by re-read and classify exact/conflict, never overwrite existing identity. |
| Crash windows | Before commit: no accepted effect, retry same ID may be applied once; after commit/before ack: retry reads ledger and returns same classification. Crash after commit/before notification dispatch: outbox pending. WAL checkpoint is not an application-level clean slate or dedupe eviction. | Same DB transaction/outbox logic. DB WAL + backup/PITR can recover committed state; define durability settings, timeline/high-water and witness before asserting any no-loss guarantee. Failover with lag can lose acknowledged commit without synchronous durability gate: fence/quarantine until independently reconciled. |
| Backup/restore | SQLite Online Backup API to an isolated destination, verify integrity/digest/manifest/epoch/witness. Never copy only `.db` and omit active WAL; test power-loss separately; verify `PRAGMA synchronous=FULL` on target FS/version and pin a SQLite version with relevant WAL fixes. | PostgreSQL base backup + continuous WAL archive/PITR under approved isolation; verify archival completeness, manifest, witness and restoration to a consistent LSN. Physical recovery does not automatically preserve application dedupe if an old timeline is promoted. |
| Tradeoffs | Lower operational complexity, no separate DB server, but single host, storage backup discipline, write contention and WAL maintenance limits. | Higher operations/security/backup/HA burden; supports multiple workers; transaction and DB failover controls still need application fencing and external anti-rollback witness. |

**Recommendation for independent review:** A for an isolated single-host *prototype*, B if verified multi-host/concurrent operation is required. Selection remains pending constraints, fault injection and A0 approval. Neither option is production GO. Official sources: [SQLite WAL concurrency/host limitation/checkpoint](https://sqlite.org/wal.html), [synchronous pragma](https://sqlite.org/pragma.html#pragma_synchronous), [SQLite Online Backup API](https://sqlite.org/backup.html), [PostgreSQL isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [INSERT/ON CONFLICT](https://www.postgresql.org/docs/current/sql-insert.html), [PostgreSQL WAL archiving/PITR](https://www.postgresql.org/docs/current/continuous-archiving.html). These document capabilities, **not** observations of this project's VPS or versions.

## 3. Saturation without unsafe eviction

A live proposal **must not simply increase 256 to a larger finite cap** or drop the oldest ID. Preserve identity rows for the entire provable replay horizon across both good/bad and interruptions; partition/index ledger by scope/epoch and monitor size, write latency, free disk/WAL/archive, backlog and estimated time-to-exhaustion. Set warning/critical thresholds from measured ingest rate, recovery time and storage headroom at later design approval, **no invented SLA here**. Rate-limit/quarantine untrusted or compromised-source floods *before* opening a transaction; do not misclassify a duplicate as a fresh interruption. No automated eviction; at capacity, fail closed on unsafe new ingest, retain identity rows, keep a **separate minimal-health/status route and independent storage/alert channel** available and non-dependent on the full ledger. Status/alert cannot silently update lifecycle state; if those fail, mark monitoring continuity `UNKNOWN/NO_GO`, escalate out of band under a reviewed runbook. This avoids the current *silent* permanent blind freeze without pretending every new good/bad can be accepted while capacity is gone.

**Authorized recovery/rotation:** operator verifies last committed high-water, backup/witness and producer health, closes intake, creates a backup and ledger/outbox audit, expands storage or archives history to authenticated immutable retention (not deletion), verifies queries for old IDs still work; drain queued safe inputs with same IDs/epoch after fence. If protocol defines a finite replay window, retire entries **only after** an authenticated producer epoch change, enforced server-side minimum event time/sequence, expiry of all possible retries/offline producers, immutable retained prior-epoch ledger and independent tests demonstrating an old ID cannot reapply after rollback. If any assumption cannot be proven, retain rows or quarantine; **no reset of entire Lifecycle** to clear pressure. Changing/rotating epoch cannot produce duplicate incident notifications; keep outbox/incident identity across rotations.

## 4. Migration, access, rollback and live gates

1. **Migration policy:** synthetic v1 with an accepted interruption lacks canonical replay evidence; D3 already rejects v1 when audit records one. Audit is unauthenticated, so even apparently clean v1/v2 **cannot be promoted as trusted live state**. Migrate only from a protected, provenance-verified live source after a separate acceptance decision. Preferred: fresh isolated epoch, intake disabled, independently verified ledger/control/outbox from trustworthy upstream event IDs or start new explicitly untrusted history *without claiming dedupe across boundary*. Existing pending alerts remain suppressed/reconciled until identity and delivery are settled. Reject corrupt/missing/oversized/colliding v2 registry and unknown version. Never infer exact payload from a hashless audit.
2. **Dry-run before any future cutover:** select alternative after independently reviewing source binding, expected volume, retention horizon, DB failure modes and cost; propose schema/adapter on separate future branch; create test-only seeded data, inject crash/disk-full/concurrency, verify expected rows/state/outbox, backup and restore against external witness. Runbook includes baseline, read-only inventory, backup integrity check, rollback rehearsal and abort criteria. Test migration *both directions*; rollback of code must not restore an older identity ledger or reissue notifications. Keep old/new readers fenced, no dual writer without explicit transaction/fence protocol.
3. **Least privilege:** producer cannot write DB; ingest service has scoped insert/update, observer read-only, worker outbox-only, operator recovery via separately audited approval, backup reader with limited rights, witness/key store independent of DB admin where possible. Separate credentials, encrypt backups and restrict retention/access; authenticate notification target and receiver. No secret, private payload or real host ID in Git.
4. **Go/no-go:** independent review of this design; A0-specific authorization for implementation and separate A0 live approval; authenticated source and replay/epoch protocol; demonstrated crash and power-loss behavior, DB-full alert continuity, cross-process uniqueness, no duplicate incident/delivery claim beyond receiver's actual contract; verified backup/restore/rollback/witness and operator runbook; tested recovery from cap while preserving dedupe; capacity metrics and on-call owner. Missing any item => `NO_GO` for live. This design does not authorize VPS change, Docker, production, paid API, PR merge or Codex.
