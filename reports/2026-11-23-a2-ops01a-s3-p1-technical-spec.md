## 2. Backend decision boundaries

| Requirement | A: SQLite WAL, single verified local host | B: PostgreSQL transactional ledger |
|---|---|---|
| Workload | One authoritative local volume, multiple local readers and at most one concurrent writer; `BEGIN IMMEDIATE`, finite busy timeout | Shared authoritative DB for multi-host/multi-worker; scope-row `SELECT FOR UPDATE`, ordered locks, finite retries |
| Reliability | `PRAGMA journal_mode=WAL`, `synchronous=FULL` assessed against pinned version/FS; SQLite is not an HA/failover platform | Explicit isolation level (proposed READ COMMITTED for scope-lock path), synchronous durability and standby policy verified; serialization retries re-open transactions |
| Locks | `SQLITE_BUSY` => bounded retry or fail-closed; no network FS for WAL | Lock scope control, fence current epoch, unique identities; on unique/deadlock/serialization conflict ROLLBACK and re-read fresh transaction/snapshot |
| Backup | SQLite Online Backup API with integrity check; never copy main DB without active WAL reconciliation | Coordinated base backup + WAL/PITR, restore LSN/timeline and archive completeness check |
| Cost | Lower initial operations, single-host bottleneck and host SPOF; storage/witness costs still exist | Operational overhead, backups, DB administration, replication/failover and witness costs |
| Gate | Default candidate for isolated local prototype, **not selected for live** | Candidate if measured scale/multi-host/failover demands justify it; **not selected** |

Both rely on the *same* schema/semantic guarantees below and an independently protected anti-rollback witness. SQLite's WAL log is not the event ledger. PostgreSQL's WAL/PITR is not itself proof that a promoted replica contains all acknowledged application commits. Official capability references (not proof on VPS): https://sqlite.org/wal.html ; https://sqlite.org/pragma.html#pragma_synchronous ; https://sqlite.org/backup.html ; https://www.postgresql.org/docs/current/transaction-iso.html ; https://www.postgresql.org/docs/current/continuous-archiving.html .

## 3. Logical schema — normative contract for future adapter design

Suggested generic relational entities and key constraints, NOT executable DDL:

1. `scope_control(tenant_id, resource_id, rule_id, rule_version PK composite; active_epoch_id, epoch_generation, revision, trusted_last_observed_at, state ENUM NORMAL/OPEN/RECOVERED, bad_streak, good_streak, incident_seq, last_alert_at, last_ledger_seq, anchor_generation)`. Exactly one current control row per scope; `revision` is monotonic; normalize timestampts to explicit UTC.
2. `producer_epochs(epoch_id PK, scope FK, server_issued_generation UNIQUE(scope,generation), authenticated_principal, key_id, min_sequence, min_event_time, status ACTIVE/FENCED/RETIRED, issued_at, fenced_at, archive_ref)`; partial uniqueness of ACTIVE per scope. Epoch creation/fencing is DB-transactional with control update; signed/authenticated envelope binds epoch, sequence and event payload to principal. Reject missing/mismatched/fenced epoch *before* ID reservation. An epoch *string* in user JSON is never sufficient.
3. `replay_ledger(scope, epoch_id, sample_id, canonical_algo_version, payload_digest, canonical_length, event_sequence, event_time, classification GOOD/BAD/INTERRUPTION, terminal_result, ledger_seq, accepted_at; UNIQUE(scope,epoch_id,sample_id), UNIQUE(scope,ledger_seq))`. One shared namespace for good/bad/interruptions. Explicit archived/prior-epoch identity index. Canonical bytes/sha256 algorithm and version retained in protected, bounded audit or collision-resistant byte store according to retention decision; digest only is an equality heuristic, not authentication. Canonicalization v1 follows D3 sorted compact finite JSON semantics but full external envelope canonicalization must be separately frozen; schema must not silently rewrite older canonical results.
4. `incidents(scope, incident_seq PK scoped, state, opened_revision, recovered_revision, incident_id)`; `incident_id` stable, monotonic sequence across epochs, and recovery/OPEN identity never resets due to archive/rotation.
5. `notification_outbox(outbox_id PK, scope, incident_seq, notification_kind, eligibility_revision, dedupe_key UNIQUE, event_payload_digest, target_id, status PENDING/LEASED/DELIVERED/UNCERTAIN/DEAD_LETTER, attempts, next_attempt_at, lease_generation, lease_owner, lease_expiry, delivery_receipt, created_revision; UNIQUE(scope,incident_seq,notification_kind,eligibility_revision))`; store sanitized payload and never access external network inside ingest TX. `DELIVERED` only with verified receiver ACK; `UNCERTAIN` on ambiguous send.
6. `backup_anchors(generation PK, scope_high_water_map_digest, ledger_high_water, control_revision, outbox_watermark, epoch_generation, schema_version, snapshot_digest, signing_key_id, witness_receipt)`; the witness itself is independently administered and durable **outside** the DB rollback/failure domain. Proposed independent status heartbeat with freshness timestamp, no false healthy default.

Foreign-key and CHECK constraints must disallow negative streaks/incident sequence, missing scope references, multiple ACTIVE epochs, impossible outbox state transitions, mismatched incident/outbox identities. Partitioning, isolation and table layout are backend-specific. A *single committed sample transaction* atomically updates replay ledger + control + incident + outbox intent + epoch generation as needed; outbox dispatch/receipt is a separate transaction. Attempt logs must be durable without raw payload or secrets.

## 4. Admission and atomic event processing

1. Authenticate principal and transport/signature; verify scoped server-side tenant/resource/rule/rule_version/epoch and envelope version; impose principal quotas and bounded payload/ID/time/sequence. Unknown, forged, oversized, malformed, non-UTC, forbidden legacy synthetic rule omission => **REJECT BEFORE LEDGER RESERVATION**. Do not grant trust from the JSON fields `source`/`rule`.
2. Validate finite canonical JSON exactly per pinned version and compute digest; verify signed event's epoch/sequence/time binding and any minimum sequence/time barrier. Old/fenced epoch and rewrapped old observation => reject before state mutation, even if some archive is unavailable (archive unavailable = quarantine).
3. Open transaction; lock per-scope control (SQLite `BEGIN IMMEDIATE`; PostgreSQL scope lock), re-read *active epoch and fence generation inside TX*. **Replay lookup before timestamp-watermark check** across ledger and archived identity index. Exact prior result returns exact replay classification with no new durable state; changed canonical payload on same key returns conflict, never correction. If existing key in different epoch, rely on authenticated epoch, sequence/time barrier and preserved old archive, not just epoch-scoped UNIQUE.
4. For a new properly attributed event require monotonic qualifying timestamp relative to `trusted_last_observed_at` (not an interruption clock). For qualifying GOOD/BAD update trusted timestamp/streaks and lifecycle transitions. For authenticated later stale/UNKNOWN/blocked **INTERRUPTION**, insert replay identity and clear both streaks but do not advance accepted GOOD/BAD timestamp, incident, state or send. Foreign/malformed/replayed events do not clear streaks.
5. Preserve S2/D3 behavior: three qualifying BAD lead OPEN; active OPEN incident sequence unchanged after more BADs; three qualifying GOOD recover; +899 suppress; +900 notify when newly eligible; +901 must not trigger an extra alert absent a newly qualified condition and cooldown. Notification eligibility and incident changes are computed once in TX and materialized as unique outbox intent; suppressions may have sanitized audit but never a send.
6. Increment scoped control revision and ledger high-water once for accepted new event, insert any incident/outbox record, commit. External ACK requires both DB commit confirmation **and anti-rollback anchor protocol** below. DB unavailability/unknown commit => no invented success, retry same authenticated ID via fresh lookup after recovery. No OPEN -> RECOVERED solely because monitoring went dark. Errors must not partially apply ledger or emit notification.

**Concurrency/error policy:** retry only before any external side effect, with bounded randomized backoff and cap set in implementation plan; upon PostgreSQL unique/serialization failure ROLLBACK, fresh transaction for winner lookup (especially REPEATABLE READ/SERIALIZABLE); if lock/time/space budget exhausted fail closed, independent degraded monitoring reports UNKNOWN. Retrying notification dispatch is distinct and obeys receiver semantics.

## 5. Epoch protocol and N01 cross-epoch replay laundering

**Decision proposed for A0 approval:** use a server-issued opaque epoch, authenticated envelope binding `(principal,scope,epoch,event_sequence,event_time,sample_id,payload_digest,canonical_version)`. The gateway must not replace E1 with E2 or silently omit epoch. Epoch transitions: (i) stop new intake/close old worker lease; (ii) verify old high-water, retained immutable identity/archive and pending outbox; (iii) atomically fence E1/create E2/increment `epoch_generation` with scope control row, commit; (iv) publish new authenticated epoch material only after persistence and witness anchor; (v) reopen intake with E2 min sequence/time barriers. Use server controlled per-epoch monotonic sequence; reject gaps/reorders according to an explicitly approved source delivery model, *not* blanket discard that could hide health events. Cross-epoch identical payload should not reapply because signed E1 cannot authenticate as E2, and same-origin observation provenance and minimum epoch barrier are enforced. If producer can truly re-sign old E1 content with E2 credentials, a trusted producer compromise has occurred; dedupe requires durable origin event ID/global issuer stream sequence or trusted upstream authority. Without that guarantee, **NO_GO** for cross-epoch no-replay assertions.

Invalidate stale in-flight ingest workers with transactional compare-and-swap of `epoch_generation` and control revision; revalidate after acquiring lock. Lease expiry alone does not prove an external sender cannot continue. Never erase E1 ledger just because E2 exists.

## 6. Anti-rollback, backup integrity and N02 ACK gap

**Critical constraint:** a database commit and a physically distinct witness write cannot be made atomic without a coordinated distributed transaction. Do **not** claim atomicity across them. Proposed conservative protocol is a *fenced, serialized, three-state commit receipt*:
- Precondition: durable independent witness service accessible; previous generation G, committed DB state anchored. Under exclusive per-scope generation allocator / fence, **reserve monotonic generation G+1 in witness before database write**, recording an intent referencing scoped revision and expected digest where possible. If witness reservation fails, do not commit/ACK. Reservation alone is NOT an event acceptance ACK.
- Apply event in DB transaction referencing reserved G+1; write control/ledger/outbox and pending `backup_anchors` record atomically; COMMIT, then re-read committed state/digest. If DB commit fails or is ambiguous, mark G+1 unresolved in witness, prohibit using it as proof of ACK, quarantine and reconcile before new generation (gaps allowed but never treated as old clean data).
- Finalize independent witness with DB commit digest/high-water and receipt. **Only after durable finalize confirmation return protected ACK** and allow ordinary outbox dispatch. If finalize times out after DB COMMIT, outcome is `COMMITTED_UNACKNOWLEDGED/UNCERTAIN`; no success ACK, quarantine intake/dispatch until independent reconcile. A lost network ACK to producer is resolved by lookup + witness proof; exact replay must not create a new outcome. On restore, reject/quarantine when DB generation/digest is older, ahead of, or inconsistent with the witness; never assume that an older *valid signed* backup is current just because its MAC verifies.
- Backup manifest covers database snapshot, ledger, scope control, epochs, incidents, outbox, schema/canonical versions, generation, LSN/SQLite checkpoint reference and signing key ID. Verify cryptographic integrity, restore integrity check and fresh witness independently. Require encrypted backup, retention, tested key rotation; no secret in repo. **Witness must be outside backup rollback domain and preferably independent administration.**
- Recovery cannot guarantee acknowledged-commit preservation if witness or authoritative event source itself can be rolled back/compromised; fail closed and report monitoring `UNKNOWN/NO_GO`. Proposal incurs independent witness cost/availability dependency; owner must approve strict ACK latency/availability versus protected receipt semantics. Any batching/asynchronous witness after ACK invalidates strict anti-rollback claim and requires explicit weaker RPO contract + quarantine of uncovered interval.
- SQLite backup via online API and WAL-consistent snapshot, PostgreSQL PITR to consistent timeline/LSN plus complete WAL archive; no assumption from backup existence alone. A database rollback for code deployment **must not** roll back replay identity or outbox.

## 7. Notification outbox, lease and N03 ambiguous sends

After an anchored commit, dispatcher selects eligible PENDING/UNCERTAIN via atomic lease claim with token/generation and expiry; only the current lease may mutate attempt/ACK state (CAS). Before transmission it must recheck current lease/fence and target idempotency key, ideally with a short dispatch permit issued against persistent lease generation. W1 holding expired lease must be denied after W2 takeover. **Unavoidable window:** W1 might already have sent bytes before losing fence or might still be in network flight after W2 takes over. Neither SQLite row lock, PostgreSQL transaction nor outbox UNIQUE guarantees exactly-once **external** effects. Where receiver supports stable idempotency key, use it and verify receiver behavior through mock + provider contract. Without it, on timeout/crash mark `UNCERTAIN` and reconcile externally before retry; automatic resend of ambiguous effect is forbidden for non-idempotent receivers. Bound retries/backoff, dead-letter threshold, attempts, lease TTL and operator escalation. Worker may not send when backup anchor/witness is unresolved, except separately approved independent degraded-health route. Quarantine stale epoch senders without deleting or suppressing existing outbox.

Monitor independent `outbox_pending_age`, `uncertain_count`, delivery failure, expired lease, receiver errors and reconciliation age. Separate lifecycle `OPEN/RECOVERED` from delivery success.

## 8. Capacity, status independence and N04 common-mode fault

Retain replay history over a *provable* replay horizon. No fixed 256-row eviction; avoid switching to fresh epoch as a shortcut. Old sample-ID lookup must remain available across archive/restore/rotation. Define projected storage exhaustion from measured sample volume, index growth, WAL/checkpoint, backup retention, and retry rates. Quota/rate-limit authenticated principals before database transaction, while retaining evidence for security escalation. When disk/WAL/ledger full, reject new unsafe inputs, preserve old ledger/outbox/OPEN and publish `UNKNOWN/DEGRADED` over **separately administered storage/network/credentials** with a bounded alert queue/rate limiting. Prove failure-domain independence against common ENOSPC, permission expiry, unavailable broker, missed heartbeat and no-on-call scenarios. If independent route fails too, never display healthy; mark `UNKNOWN/NO_GO` and use documented out-of-band operator escalation. Do not invent an uptime SLA or claim continuous alerting without a real external observer.

## 9. Operations boundaries, permissions and migration

- Ingest principal cannot directly modify DB; writer scoped DML, observer read-only, outbox dispatcher only bounded outbox rights, backup operator restore under audited separation of duties, witness/key owner separately privileged. Use least privilege, key rotation/revocation and backup secret protection.
- Synthetic v1/v2 snapshot `restore()` is unauthenticated and must not be directly promoted to trusted live ledger. v1 with interruption audit cannot be reconstructed; v2 JSON with removed interruption history cannot become a trusted live restore. Require provenance-verified migration, fenced drain, no dual writers, dry-run and approved rebootstrap for unverifiable state. New adapter must prove source semantics equivalence before migration.
- Startup validation: version/schema, database integrity, active epoch, witness generation, pending outbox, last trusted timestamp, incident ID and archived lookup. Reject unsafe downgrade or stale replica promotion. All release/runtime tests remain unexecuted.
- Prototype plan must pin engine version, OS/FS, storage type, topological trust boundaries, schema migrations, exact failpoints, receiver mock, backup/witness mock AND later production-like independent witness trial, cleanup and rollback; production remains separate STOP.
- Observability minimum: admission rejects by reason, replay exact/conflict, txn conflict retries, anchor generation/age, witness unavailable, ledger growth, storage/WAL, backup verification, outbox PENDING/UNCERTAIN, lease fences, last good external heartbeat. Only sanitized structured logs, no payload/token.
